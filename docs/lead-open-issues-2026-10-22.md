## 问题 1：中心不在物理中心 + 绘制时间越长越卡、掉帧

### 1.1 现象

- MGC3130 报告的坐标原点不在用户认定的物理工作区中心，整体偏左。
- 录制时间越长，界面越卡，掉帧越明显；无法判断是传感器、链路还是软件。

### 1.2 已有证据

对仓库内两次独立采集（`tools/capture_fast_01.csv`、`capture_fast_02.csv`，由采集工具直接写盘，不经过 UI）：

| 指标 | fast_01 | fast_02 |
| --- | --- | --- |
| 帧数 / 跨度 | 968 / 29.39 s | 933 / 29.86 s |
| 有效帧率 | 32.9 Hz | 31.2 Hz |
| 帧间隔 p50 / p95 | 31.0 / 47.0 ms | 31.0 / 47.0 ms |
| 最大停顿 | 1141 ms | 1734 ms |
| >250 ms 的停顿次数 | 3 | 5 |
| 原始日志吞吐 | 3.98 KB/s | 3.98 KB/s |

推论：

1. UART 链路未饱和。`115200 8N1` 上限约 11.5 KB/s，实测 3.98 KB/s（约 35%）。FPGA 发出的是 14 字节二进制帧（[mgc_uart_report_tx.sv](../rtl/mgc_uart_report_tx.sv)），理论上限约 820 帧/s，而实测 32 帧/s。限速点在 UART 上游（I²C 轮询周期、传感器输出率或 USB 串口驱动）。
2. 秒级停顿比稳态帧率危害更大。100 BPM 下一个 16 分音符为 150 ms，1734 ms ≈ 11 个 16 分音符无数据，会被编译成整段 rest。
3. 这批数据由独立采集工具产生，**不经过 UI**，因此"掉帧"至少有一部分不是界面造成的。

UI 侧两个确定的放大器（不是已证实的根因）：

- [synthwave_ui.py](../pc_receiver/synthwave_ui.py) `_poll_inbox` 把 `_draw_canvas()` 写在逐条取记录的循环内，一次轮询积压 N 条记录就整幅重绘 N 次，而每次重绘成本随历史点数线性增长。
- 实测单次全重绘成本：500 点 0.37 ms、2000 点 0.56 ms、8000 点 2.10 ms、16000 点 4.21 ms。40 ms 轮询预算下，积压 8 条 × 8000 点即约 17 ms，随录制时长逼近并超过预算，形成"越画越卡 → 积压更多 → 更卡"的正反馈。
- `create_line(..., smooth=True)` 在数千点规模上没有收益，只增加 CPU。

中心偏移的具体影响：起笔门控把左边缘硬编码为原始 `4096/65535`（[synthwave_loop.py](../tools/synthwave_loop.py) `LEAD_LEFT_EDGE_MAX`），假设原始 x≈0 即物理可达左沿。若工作区整体偏移导致手够不到该值，门控可能打不开或只在极端姿势下打开。

### 1.3 待验证假设

| 编号 | 假设 | 验证方式 |
| --- | --- | --- |
| H1 | 掉帧发生在 UI 之前（传感器/链路/SDK） | 实验 A：绕过 UI 单独运行接收器 |

### 1.4 实验 A：绕过 UI

```powershell
pc_receiver\Static-Release\mgc3130_receiver.exe --seconds 20 --output solo.jsonl
python tools\analyze_frame_timing.py solo.jsonl
```

判读：

- 若仍有 31 ms 主峰、秒级停顿或 `SDK skipped > 0` → 结论偏向 H1，UI 不是根因。
- 若帧间隔稳定在 5–10 ms 且无长停顿 → 结论偏向 H2，问题在 UI 消费端。

### 1.5 实验 B：区分传感器出帧率与串口发出率

```powershell
python tools\probe_loop_uart.py --port COM9      # 识别哪一路带 LOOP UART READY
python tools\loop_control_uart.py --port COM9 diag
```

取两次 diag 的 `report_count` 差值 ÷ 间隔秒数：

- 若 ≈ 200 Hz 而串口只有 32 Hz → FPGA 侧在丢帧/降频（检查 `mgc3130_reader` 轮询与 TX 背压）。
- 若 ≈ 32 Hz → 传感器或 I²C 轮询本身就是 32 Hz，链路无辜。

### 1.6 实验 C：UI 消费端

在 UI 的接收线程里记录每行的本地到达时间戳（`time.monotonic()`），与记录中的传感器 `timestamp_ms` 对比。若到达时间成簇而传感器时间均匀 → 消费端积压。

### 1.7 实验结果（2026-10-22，第一轮）

> **勘误（同日）**：下面 COM9/COM10 的测量来自 FPGA 板链路，而当前实际使用的是 **MGC3130 SDK 直连 USB**，不经过 FPGA。该组数据与本文问题无关，仅保留为旁证。真正的归因见 §1.9。

**实验 A（单独运行接收器）**：设备在线（`gestic_open` 成功），但 20 秒内 **0 条 position 记录**。原因是无手在场时 SDK 几乎不发帧；偶发空闲帧的签名是 `x=y=32767, z=65535`。结论：

- 该流是**存在感应门控**的，空闲帧率不能当作基线，实验 A 必须在有人做手势时进行。
- `z=65535` 是"无手/空闲"的值，恰好等于 Z 轴最大值。任何按 Z 调度横向增益的实现都必须先区分"无手"与"高 Z 姿态"，否则会把 rest 当成最高深度。

**实验 B（FPGA 链路）**：

| 端口 | 结果 |
| --- | --- |
| COM9 | 存在但打不开（打开超时），当前不可用 |
| COM10 | 可打开，二进制帧（`FE FF` 同步），10.14 s 收到 5874 字节 / 245 帧 |

COM10 测量值：

```text
吞吐      579 B/s     （115200 8N1 上限约 11520 B/s，占用 5%）
帧率      24.2 帧/s
消息 ID   0x16 × 244、0x10 × 1
```

判读：

1. 链路占用仅 5%，**传输不是瓶颈**，不存在"串口发不完"导致的丢帧。
2. [mgc3130_reader.sv](../rtl/mgc3130_reader.sv) 没有轮询分频器，它在 `ST_WAIT_TS` 等传感器的 data-ready 后立即读 I²C（100 kHz），因此 **24 帧/s 的节拍来自传感器，而不是 FPGA 定时器**。
3. `probe_loop_uart` 对 COM10 没有收到 ACK，说明当前板上不是 loop 控制固件，**CSR 的 `report_count` 实验 B 暂不可用**；需要先烧 loop 位流。
4. 之前 CSV 里的 31 ms 主峰（32 Hz）与本次线上 24.2 帧/s 同量级，互相印证"稳态帧率由传感器决定"。

仍未解释的部分：CSV 中 1.1–1.7 s 的停顿。它既可能来自传感器/驱动，也可能来自采集端的 USB 缓冲，必须在有人做手势的情况下重测才能定位。

### 1.9 勘误：真实链路与两个新发现

**链路更正**：当前是 `MGC3130 → USB HID → gestic_api.dll → mgc3130_receiver.exe → stdout 管道 → Python UI`。全程没有 UART，因此 §1.7 的 FPGA/COM 测量不适用；"链路带宽不是瓶颈"这一结论在 USB HID 上仍需重新验证，但至少 UART 那部分可以排除。

**发现 1：仓库里的 exe 是旧二进制。** `pc_receiver/Static-Release/mgc3130_receiver.exe` 构建于 2026-10-19 17:25，而 `mgc3130_receiver.cpp` 最后修改于 2026-10-21 21:25。旧 exe 输出的是旧 schema（`frame`，没有 `sequence_gap` / `position_valid`），与源码不一致。已于 2026-10-22 用 MSBuild `Static-Release / Win32` 重建，新输出包含：

```json
{"type":"position","timestamp_ms":...,"sequence":...,"sequence_gap":...,
 "x":...,"y":...,"z":...,"position_valid":null,...}
```

影响：`sequence_gap` 就是 `gestic_data_stream_update()` 返回的 `skipped`，即 **SDK 内部丢帧计数**，是本次归因最关键的指标，而旧二进制根本不输出它。

**发现 2：接收器主循环的节奏与背压。** `mgc3130_receiver.cpp` 的实现是：

```cpp
do { result = gestic_data_stream_update(&gestic, &skipped); ... } while (result == GESTIC_NO_ERROR);
Sleep(5);
```

每轮先排空 SDK 队列，再固定睡 5 ms。单看这不丢帧，但它把"排出速度"交给了 stdout 写入：每行 `std::cout << line; flush;` 是**同步阻塞写**。UI 以子进程管道读取，一旦 UI 变慢、管道缓冲填满，接收器就阻塞在 `write()` 上，期间不再调用 `gestic_data_stream_update()`，SDK 环形缓冲溢出 → `skipped` 增长 → 表现为"越画越卡、掉帧越多"。

这条机制与"随绘制时间增加而卡顿"高度吻合，也是当前最值得验证的假设。

### 1.11 结论（2026-10-22，第二轮：SDK 直连实测）

用户以重建后的接收器单独录制 20 秒（手持续移动），得到 3701 条 position 记录。核算结果：

| 指标 | 数值 |
| --- | --- |
| 记录数 / 跨度 | 3701 / 18.50 s |
| 有效帧率 | **200.0 Hz** |
| `timestamp_raw` 相邻差值 | 全部为 1（3700 次），无跳号 |
| `sequence_gap` 非零 | **仅第 1 条**（`sequence_gap=133`） |
| `timestamp_ms` 唯一值 | 1179 个 / 3701 帧（平均 3.14 帧共用一个时间戳） |
| `timestamp_ms` 差值分布 | 0 ms × 2522、15 ms × 439、16 ms × 733、31 ms × 5、32 ms × 1 |
| 最大间隔 | 32 ms，无 >250 ms 停顿 |

四条结论：

1. **数据源是健康的。** 200.0 Hz、帧计数严格递增、启动之后零丢帧。之前 CSV 里的 32 Hz 和 1.1–1.7 s 停顿属于 FPGA 链路（§1.7），与当前问题无关。
2. **启动瞬态丢 133 帧**（约 0.66 s）：发生在第一条 `gestic_data_stream_update()` 之前，是打开设备到开始排空之间的积压，之后不再发生。对音乐无实际影响，但会表现为录音开头的 133 个 prestart 帧。
3. **真正的缺陷在时间基**：接收器用 `GetTickCount64()` 打时间戳，分辨率约 15.6 ms，所以 68% 的帧与前一条共用时间戳。100 BPM 下一个 16 分是 150 ms，15.6 ms 相当于 10%；而 Lead 的 128 tick 重采样、`a_rel` 归一化和锚点 tick 全部建立在这个 `timestamp_ms` 上。**这不是精度瑕疵，是时间轴本身被量化成了台阶。**
4. **"掉帧"是渲染现象，不是数据丢失。** UI 的接收线程与无界队列始终在排空，接收器不会因 UI 变慢而阻塞（`stdout` 由独立线程持续读取）。真正的问题是主线程每条记录重绘一次、且重绘成本随历史长度增长，于是"看到的更新"越来越稀疏——观感是掉帧。

### 1.12 已实施的修复

**第一轮**（`d5168df`）：`_poll_inbox` 改为每轮只重绘一次、33 ms 节流、按步长把画布点抽稀到约 1500 点。复测仍报卡顿，说明这一轮没有打到根因。

**负载实验（用于定位）**：两级测量，都是 200 Hz 灌入：

| 场景 | 结果 |
| --- | --- |
| 合成负载，40 s，直接写 inbox | 队列峰值 25、常驻 0；draw 1.5–3.6 ms；画布图元恒定 39 个 |
| 真实子进程 + stdout 管道 + pump 线程，回放 3701 帧 | 队列峰值 7；draw 1.2–4.4 ms；无累积 |

两级都排除了"数据积压"和"图元泄漏"。真正的四个原因：

1. **步长抽稀会随采集长度加重走样**：`stride = 总点数 / 1500`，越画越大，细笔触被直接丢掉——这就是"后期无法精细绘制"。
2. **`smooth=True` 把用户画的尖角磨圆**，看起来像"失真"。
3. **33 ms 节流 + 40 ms 轮询 = 70–100 ms 视觉延迟**，就是"拖拽感"。
4. **每次重绘都全量重扫采集**，成本 O(n)，与第 1 点叠加。

**第二轮**（本次）：

- 用 `_thin_path()` 替代步长抽稀：先投影到整数像素，再丢弃落在同一像素的点。画出的形状在显示分辨率下是精确的，且成本由画布面积决定，与采集长度无关。
- 新增 `_PixelPathCache`：只投影自上次绘制以来新增的样本，重绘不再全量重扫。
- 轮询 40 ms → 16 ms，去掉 33 ms 节流（绘制本身约 1.7 ms，可承受 60 fps）。
- 去掉 `smooth=True`，尖角保持原样。
- 新增每秒刷新的诊断行：`xxx Hz · queue n · draw x.xx ms · N frames`，用于现场判断是采集、队列还是绘制的问题。

实测：3701 帧、29.6 s 内 draw **1.53 → 1.70 ms**，与采集长度基本无关。

测试：[pc_receiver/test_synthwave_ui_helpers.py](../pc_receiver/test_synthwave_ui_helpers.py) 8 项，覆盖像素去重、顺序、面积上界、退化画布，以及增量缓存与一次性抽稀的等价性。

**诊断落盘（同一轮）**：为了避免靠人读屏幕判断，UI 现在把两样东西写进文件：

| 文件 | 内容 |
| --- | --- |
| `pc_receiver/diagnostics/ui_<时间戳>.csv` | 每秒一行：`wall_ms, elapsed_s, state, rate_hz, queue, draw_ms, frames, preview_points, drawn_points, canvas_w, canvas_h`；空闲时也写，所以"设备没出数据"会直接表现为 `rate_hz=0` |
| `pc_receiver/captures/<track>_<时间戳>.jsonl` | 接收器的原始帧（通过 `--output`），与 UI 的显示路径无关，可用于事后回放 |

两个目录都写进 `.gitignore`。若 `--output` 路径不可写，`_prepare_capture_path()` 返回 `None`，接收器退回只写 stdout，不会因为保存失败而丢掉整次录制。诊断写入也包在 `try/except OSError` 里，绝不影响界面。测试增至 10 项（新增表头只写一次、未知字段不报错）。

未修复（需要决策）：结论 3 的时间基。建议改为 `QueryPerformanceCounter` / `std::chrono::steady_clock` 打到达时间，并用 `timestamp_raw`（5 ms/帧，已验证严格递增）生成均匀的 `logical_time_ms` 供编译器使用。这会改变喂给 Lead 的时间轴，属于设计变更，不能顺手做。

### 1.13 第三次实测：真实演奏采集（19:32）

用带诊断落盘的版本录了一段真实演奏（`pc_receiver/captures/lead_20261022-193218.jsonl`，`diagnostics/ui_20261022-193216.csv`）。

**性能读数（26 s，4938 帧）**：

| 指标 | 数值 |
| --- | --- |
| `rate_hz` | 197–203（首秒 189，末秒 89 为停止） |
| `queue` | 全程 0–3 |
| `draw_ms` | 1.0–1.6，无上升趋势（t=5 s 为 1.5，t=27 s 为 1.4） |
| `drawn_points` | 180 → 2785（像素去重后的上界，随画面稳定） |
| 画布 | 856 × 410 |

结论：**UI 在真实链路上没有落后**。队列不积压、重绘不增长，与合成负载的结论一致。

**采集质量**：4938 帧 / 24.77 s / 199.3 Hz，帧计数 4937 次全部 +1，无丢帧（仅 1 条启动 skip）。`timestamp_ms` 唯一值 1581 / 4938（3.1 帧/戳），15.6 ms 量化仍在。

**横向裁剪**：`x=0` 占 5.3%、`x=65535` 占 3.7%、`y=0` 占 1.4%。说明这段演奏两端都撞到了传感器量程边界——这是"中心不在物理中心"在数据上的表现，但**不能用运动中的中位数反推物理中心**，仍需 neutral 采集。

**Z→XY 抖动（同一方法：11 帧高通）**：

| Z 区间 | 样本 | 横向抖动中位数 |
| --- | --- | --- |
| 0–4000 | 686 | 13 |
| 4000–8000 | 3349 | 13 |
| 8000–12000 | 699 | 10 |
| 12000–20000 | 54 | 12 |
| 20000–40000 | 77 | 1 |
| 40000–66000 | 73 | 3 |

`corr(z, 横向抖动) = −0.119`。常用演奏高度（中位 6289，p95 9158）内的横向抖动只有 10–13 counts（约满量程 0.02%），**在这条 SDK 链路上，常用高度带内几乎没有 Z→XY 耦合**。§2.2 里 +0.61 的强相关来自 FPGA 链路，且主要发生在 z>24000，而本次采集在该区间只有 204 帧。

因此 **Z 增益调度不应现在实现**：先做 depth-only 采集，确认漂移真正出现的 z 阈值；如果只在高 z 出现，正确做法是"高 z 限带/保持"，而不是全局增益调度。

**编译结果**（同一份采集）：`status=ok`、`coverage=0.918`、门控接受 4533/4938、15 个音、C4–C5、tick 11–127。`move` 与 `hold` 锚点均为 0——起点是 prestart rest，首帧不是有效 move，这条值得单独处理。

### 1.14 长录制复测：重绘仍随路径长度增长（2026-10-22 19:36 / 19:37）

用户追加两段更长的录制，推翻 §1.13 的"已经平坦"结论。同一份诊断 CSV 覆盖三次录制：

| 录制 | 时长 | 帧数 | 绘制点数峰值 | `draw_ms` 范围 |
| --- | --- | --- | --- | --- |
| 19:32 | 26 s | 4938 | 2785 | 1.0–1.6 |
| 19:36 | ~68 s | 13059 | **7030** | 1.7 → **7.1** |
| 19:37 | ~52 s | 10305 | 5404 | 1.5–4.9 |

`draw_ms` 与绘制点数近似线性（约 0.7 µs/点）。§1.13 之所以看起来平坦，是因为那次只有 2785 点——**测量窗口太短**。

根因：像素去重只消除**连续**重复，手来回覆盖同一片区域时仍会累积不同的像素点，12800 个采样最终产生 7000 个不同像素点，没有真正的上界。

修复：`_PixelPathCache` 增加 `limit=2500`，超过后按半数抽稀（摊还 O(1)），把折线点数压到固定预算。实测 7030 点 5.2 ms → 2500 点约 1.8 ms，与录制长度脱钩。测试增至 11 项（新增"长路径不超预算"）。

同时修掉诊断的一个 bug：`start_record` 重置 `current_capture` 时没有重置速率窗口，导致新一段的第一行出现 `rate_hz=-12853` 这类负值。现在起点一起重置。

**仍未解释**：用户报告"音频节奏越来越慢"。UI 进程内没有音频输出路径（`play_preview` 只是渲染 WAV 后用系统播放器打开），因此这一现象无法用绘制开销解释，需要先确认音频的实际来源。

### 1.15 显示范围与饱和（2026-10-22 19:44）

用户反馈：UI 的绘制范围与传感器的可用范围不是 1:1，"右侧 UI 范围大但传感器识别范围小"，观感像掉帧和锯齿。

四段采集汇总（41118 帧）：

| 指标 | 数值 |
| --- | --- |
| x p1..p99 | 0 .. 65535（满画布） |
| y p1..p99 | 0 .. 58283（约 89%） |
| x=0 / x=65535 | 1.3% / 2.1% |
| y=0 / y=65535 | 1.05% / 0% |

结论：**不是整体范围偏小，而是两端饱和**。手到量程边缘后读数被钉在 0 或 65535，而这一段在画布上占的横向距离并不小，于是表现为"物理上还在动、画面上已经不动"——被读成掉帧或锯齿。

本轮改动：

- `_project_point` 不再逐点取整。之前每个采样都四舍五入到整像素，平滑的 1 px/步 路径会变成"几段直线 + 跳变"，这是锯齿的直接来源。现在缓存仍按整像素去重，但绘制坐标保持浮点。
- 新增 `VIEW_X_RANGE` / `VIEW_Y_RANGE`，路径与音级向导线**共用同一映射**，保证画面与音高网格始终 1:1；更换范围时两者不会脱节。当前为满量程。
- 新增 `_clip_percent()`，诊断行与 CSV 增加 `clipped_pct`：把"饱和"直接显示成数字，而不是让人误判为丢帧。

待做（需要一次 workspace 扫掠采集）：测出传感器的**线性带**边界，把 `VIEW_*` 与 `CalibrationProfile.offset/scale` 一起改成该区间。只有那时画面与音高才是真正的 1:1。

### 1.16 方形感知区与各向异性（2026-10-22 19:50）

用户补充：传感器识别区是**正方形**，并沿边缘顺时针绕行一周采集（`lead_20261022-195051.jsonl`，2449 帧）。

测量：

| 量 | 数值 |
| --- | --- |
| x 范围（含贴边） | 0 .. 65535 |
| y 范围（含贴边） | 0 .. 65534 |
| x 贴边占比 | x=0 34.5%、x=65535 24.1% |
| 最长连续贴边 | x=0 共 477 帧（≈2.4 s）、x=65535 共 457 帧 |
| 去除贴边后 | x 1..65534、y 5..65534 |

结论：范围本身覆盖满量程，贴边是手停在边沿造成的；**真正的"不是 1:1"来自画布各向异性**。绘图区 800×354 px，两个轴都铺满 65535，于是横向 82 counts/px、纵向 185 counts/px——纵向被拉粗 2.26 倍。正方形会画成扁矩形，纵向抖动被放大成台阶。

修复：

- 新增 `_plot_rect()`：两个轴共用一个 scale，内容按比例居中（letterbox）。正方形工作区现在画成正方形。
- 绘制区加显式边框，让左右留白被理解为"方形区域"，不再像丢失的量程。
- 音级向导线改用同一 `_plot_rect()`，与路径严格对齐。
- 新增测试：`test_a_square_workspace_draws_as_a_square` 把"1:1"这条要求固化成断言。

### 1.17 "音频节奏越来越慢"的实测结论

用户确认音频来自 UI 的 `PLAY PREVIEW` 生成的 WAV。把三段采集分别编译渲染：

| 采集 | bpm | WAV 时长 | Lead 音符数 |
| --- | --- | --- | --- |
| 19:41 | 100 | 20.40 s | 5 |
| 19:50:27 | 100 | 20.40 s | 4 |
| 19:50:51 | 100 | 20.40 s | 4 |

**文件本身节奏恒定**（19.2 s 循环 + 1.2 s 尾音），不可能变慢。变化的是**事件密度**：19:32 那段有 15 个音，这两段边缘 loop 只有 4–5 个音。同样 20 秒里音少了，听感就是"越来越慢"。

这是编译器的问题，不是播放或时钟的问题：沿闭合边缘绕行时，方向变化少、`move`/`hold` 锚点为 0，`compile_lead` 只能靠少量 `turn/apex/valley` 出音。需要单独决定是否给 Lead 增加"最小事件密度"或"闭环轨迹"的处理策略——这会改变音乐结果，必须同步设计文档。

## 问题 2：Z 方向移动伴随 XY 漂移，且随 Z 升高而增大

### 2.1 现象

手的深度（Z）移动会同时带来 X/Y 位移；Z 越高，XY 漂移越大。

### 2.2 已有证据
对 `capture_fast_01/02` 做 11 帧高通（去除慢速移动）后，按 Z 分箱统计横向残余抖动（单位：原始坐标，满量程 65535）：

| Z 区间 | 样本数 | 横向抖动中位数 |
| --- | --- | --- |
| 0–8000 | 759 | 106 |
| 8000–16000 | 70 | 397 |
| 16000–24000 | 38 | 523 |
| 24000–32000 | 26 | 668 |
| 32000–48000 | 44 | 641 |
| 48000–66000 | 31 | 5965 |

`corr(z, 横向抖动) = +0.614`（fast_01）、`+0.624`（fast_02）。低 Z 约为满量程的 0.16%，中高 Z 约 1%，最高段接近 9%。

限制：这两次采集是横向扫掠，不是"固定 XY 只动 Z"，因此**只能证明噪声随 Z 增大，不能用来拟合 `g_x(z)` / `g_y(z)` 系统性偏移**。后者需要按 10-21 文档 §3.4 做 depth-only 采集。

### 2.3 候选方案（尚未实现）

按 Z 调度横向增益与门限，而不是直接限速度：

```text
z_norm = (z - workspace_min_z) / (workspace_max_z - workspace_min_z)
lateral_gain(z) = clamp(1 - (z_norm - 0.25) / (0.70 - 0.25), min_gain, 1.0)
q_track += lateral_gain * (q_target - q_track)
dead_zone(z) = base_dead_zone * (1 + 3 * z_norm)
z_norm > hold_threshold → 显式 HOLD 状态
```

已知风险：

- 硬冻结会在离开高 Z 区时产生位置跳变，被锚点编译器读成 `TURN`/`APEX`，凭空生成音符。
- 限速度会改变曲线时间形状，与 128 tick 重采样和 4 tick 最小锚点间隔冲突；因此选择调增益与门限。

### 2.4 待决策

高 Z 是"纯长音区"（`min_gain ≈ 0.05`，完全失去音高控制）还是"迟钝但可控"（`min_gain ≈ 0.15–0.25`，仍会缓慢漂移）。该选择决定 `min_gain` 与 `hold_threshold`。

## 问题 3：能否用关联 XYZ 二次计算曲线，而不只是滤波

### 3.1 问题

曲线数据是否可以不直接取自单帧传感器 XYZ，而是用其他关联的 XYZ 经二次计算（状态估计）得到？三维定位领域是否有先例？

### 3.2 先例与适用范围

| 方法 | 先例 | 对 MGC3130 的适用性 |
| --- | --- | --- |
| 卡尔曼/UKF，常速度模型，观测噪声随 Z 调整 | AR/VR 手柄与手部跟踪 | 可用，且天然实现"高 Z 更平滑" |
| IMM（静止/慢速/快速多模型） | 雷达跟踪、手势识别 | 可用，适合区分抖动与有意运动 |
| 交叉轴灵敏度矩阵 | MEMS IMU 六面标定 | 可用，`g_x(z)`/`g_y(z)` 是一阶特例 |
| 工作点相关的偏置查表 / LOWESS 残差 | 磁跟踪畸变校正、数位板标定 | 可用，10-21 文档已规定 |
| 高斯过程 / 小型网络拟合残差 | 触摸笔校准、EIT 重建 | 谨慎：破坏可解释与可复现，只允许离线 profile |
| 阻抗断层成像（EIT）反演真实手位 | 电容/电场传感阵列 | 不可用：MGC3130 只输出已解算 XYZ |
| 增加 IMU / ToF / 超声测距做融合 | 多传感器融合 | 唯一能真正提升三维精度的路径，需要改硬件 |

### 3.3 当前判断

- 可行且有收益：一阶去耦 + Z 相关噪声模型的卡尔曼平滑 + Z 增益调度。三者叠加可把中高 Z 的抖动从约 1% 压到 0.2% 量级，且全程可解释、可回放。
- 不可行：仅凭单颗 4 电极电场传感器的 XYZ 输出重建真实三维位置。信息量不足，复杂模型只会拟合噪声。
- 换硬件是唯一根治路径；软件只能提高可用性。

### 3.4 待决策

是否接受"离线 batch 估计"（可复现、可审计）作为默认，实时路径只保留有界的一阶滤波；还是允许实时运行卡尔曼（需要记录状态初值与协方差以保证确定性）。
